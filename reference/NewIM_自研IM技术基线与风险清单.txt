NewIM 自研即时通讯系统技术基线与风险清单
版本：v1.0
整理日期：2026-09-20

============================================================
0. 文档定位
============================================================

本文件用于指导 NewIM 从零实现一套独立、可闭源商用、可长期维护的即时通讯基础设施。

原则：
1. 不猜测厂商内部实现。
2. 厂商事实仅引用官方文档、官方 GitHub Issues/PR/仓库。
3. “NewIM 应如何设计”属于基于公开事实提炼的工程决策，不代表各厂商一定采用相同实现。
4. 可以参考公开功能、公开架构、故障案例、Issue、PR；不要直接复制受 AGPL/商业许可约束的客户端源码。
5. OpenIM 官方当前说明：OpenIMServer/ChatServer 为 Apache-2.0；OpenIMClientSDK 为 AGPL-3.0。
6. NewIM 的真正目标不是“能聊天”，而是：
   - 不丢消息
   - 可恢复
   - 可去重
   - 可排序
   - 可观测
   - 可升级
   - 弱网下行为可预测
   - App 被杀、切网、重连后可恢复一致状态

============================================================
1. OpenIM 公开资料中值得借鉴的真实问题
============================================================

1.1 客户端 SDK 不是 WebSocket 包装层

OpenIM 官方对 OpenIMClientSDK 的公开能力包括：
- 网络管理与智能心跳
- 消息编解码
- 本地消息存储
- 关系数据同步
- IM 消息同步
- 跨平台通信与回调管理

结论：
成熟 IM 的核心难点集中在“同步、本地状态、重连、一致性”，不是单纯建立 WebSocket。

1.2 生产版本必须固定稳定 Tag

OpenIM 官方部署文档明确建议：
- 使用 GitHub Releases 中的稳定版本
- 不直接使用 main
- 不使用 alpha/beta/rc 作为生产版本

NewIM 要求：
- serverVersion / sdkVersion / protocolVersion / dbSchemaVersion 全部独立版本化
- 生产部署只能使用可追溯 release
- main/develop 不直接进生产

1.3 OpenIM Server Issue #3449：重连与多端登录状态竞争

公开 Issue 描述：
- 集群模式
- 客户端断开后短时间重连
- token / 多端登录检查之间出现状态竞争
- 可能发生“刚重连后又被踢下线”

NewIM 注意：
- 不要简单使用 userId -> connection
- 至少区分 userId / deviceId / sessionId / connectionId / tokenId
- “踢下线”必须明确踢哪个设备、哪个会话、哪个连接
- 多实例间必须同步连接所有权

1.4 OpenIM SDK Core Issue #1085：SQLite / Seq Gap

公开 Issue 描述：
- iOS/Android
- SQLite DB 频繁被写满
- 与 Seq Gap 消息相关

NewIM 注意：
- seq gap 恢复任务必须分页
- 不允许 gap 临时数据无限增长
- 本地 DB 必须有裁剪、迁移、容量监控
- gap 任务需要去重、重试上限、失败恢复
- 媒体二进制不要直接塞进消息数据库

1.5 超大会话数的同步风险

OpenIM SDK Core 公开 Issue 列表出现：
- 超过 100,000 个会话时
- 拉取所有会话 max_seq 存在性能风险

NewIM 禁止：
每次登录或重连全量扫描所有会话状态。

必须支持：
- Conversation Delta Sync
- cursor/version
- 分页
- changed-since
- 新设备 Bootstrap 与老设备 Incremental Sync 分离

1.6 在线状态不是绝对真值

OpenIM SDK Core Issue #1115 报告：
- OnUserStatusChanged 某些真实状态变化不触发

NewIM 结论：
presence 必须按易失状态设计：
- ONLINE
- RECENTLY_ACTIVE
- OFFLINE
- UNKNOWN

服务端使用 TTL；
客户端不应把一次在线事件永久当成真值。

1.7 Fresh Device 需要单独优化

OpenIM Server 公开 PR 中出现：
- optimize fresh device conversation sync

说明：
“新设备首次登录”和“日常断线重连”不是同一种负载。

NewIM 应分别提供：
- Bootstrap Sync
- Delta Sync

============================================================
2. 融云官方文档暴露的关键 IM 问题
============================================================

2.1 弱网 ACK 不确定会导致重复消息

融云官方明确描述：
- A 发送消息
- 服务端已经收到并下发给 B
- A 因弱网没收到 ACK
- A 认为失败后重发
- B 可能收到重复消息

NewIM 必须：
clientMsgId 在一次逻辑发送生命周期内永远不变。

服务端唯一约束：
UNIQUE(sender_id, client_msg_id)

同一个 clientMsgId 再次到达时：
- 不创建第二条消息
- 返回第一次持久化得到的 serverMsgId / seq

2.2 排重与性能存在取舍

融云官方文档说明：
- SDK 有排重机制
- 本地数据很大时，排重可能造成接收卡顿

NewIM 排重必须依赖索引键：
- serverMsgId UNIQUE
- (senderId, clientMsgId) UNIQUE
- (conversationId, conversationSeq) INDEX

禁止：
每收到一条消息扫描整张历史表。

2.3 UI 过滤重复不足以保证未读正确

融云官方文档提到重复消息可能带来：
- 撤回只能撤回其中一条
- UI 虽过滤重复，但未读数可能仍增加两次

NewIM 原则：
去重必须发生在：
“消息进入本地状态机和未读统计之前”。

============================================================
3. 腾讯云 IM 官方文档值得吸收的精华
============================================================

3.1 群消息 SEQ

腾讯云官方明确：
- 每个群维护消息 SEQ
- 普通群消息的 SEQ 服务端递增
- groupID + SEQ 可定位消息

NewIM 设计决策：
建议所有 conversation 都使用服务端分配的 conversationSeq。

这是 NewIM 的设计选择，不是声称腾讯 C2C 一定如此。

好处：
- 单聊/群聊统一同步模型
- unread/readSeq 更容易建模
- gap detection 简单
- 排序不依赖客户端时间

3.2 时间戳不足以保证排序

腾讯云官方 FAQ 明确包含：
“同一秒级内消息可能乱序”。

NewIM：
禁止仅按 timestamp 排序。

排序优先：
1. conversationSeq
2. serverMsgId
3. serverTime 仅用于展示和辅助

3.3 历史消息必须分页续拉

腾讯云官方支持：
- 分页拉取
- sequence/time 跳拉
- nextMessageSeq / nextMessageTime 续拉

NewIM API 应支持：
GET /conversations/{id}/messages?beforeSeq=...&limit=...
GET /conversations/{id}/sync?afterSeq=...&limit=...

禁止：
一次返回全部历史消息。

3.4 在线消息与持久化消息要分离

腾讯云官方区分：
- 在线消息：只在线下发，不做长期漫游
- 非在线消息：服务端/SDK 存储，可漫游

NewIM 应定义：

PERSISTENT
- 文本
- 图片
- 语音
- 礼物
- 系统关系消息
- 撤回/编辑事件

EPHEMERAL
- typing
- recording state
- presence heartbeat
- 临时动画信令

不要让 typing/presence 进入永久消息表。

3.5 多端是核心能力，不是附加项

腾讯云官方提供：
- 多端登录策略
- 被踢离线状态
- 删除会话多端同步
- 同平台设备数配置

NewIM V1 若不完整支持多端，必须明确限制：
- 一个移动端设备
或
- 每个平台一个设备

不要因为“技术上能连多个 WebSocket”就宣称支持多端。

3.6 Webhook 必须幂等、可扩展

腾讯云官方第三方回调文档明确：
- 回调有超时
- 某些场景会重试
- 回调包未来可能新增字段
- 接入方应兼容新增字段

NewIM Webhook 必须：
- eventId 唯一
- 签名验证
- timestamp + nonce 防重放
- 消费端幂等
- 未知字段忽略
- schemaVersion
- 不阻塞核心消息事务

============================================================
4. Push 与 IM 长连接必须分离
============================================================

腾讯云官方明确区分：
- 在线推送：长连接
- 离线推送：APNs / Android 厂商通道

融云官方也列出多厂商 Push 通道。

NewIM 推荐：

MessageService
  ↓
DeliveryRouter
  ├─ WebSocket Online Delivery
  └─ Offline Push

Push 不是消息真相源。

客户端点击 Push 后：
仍以服务器 Sync 结果为准。

禁止：
收到 Push payload 直接永久写成最终消息。

============================================================
6. WebSocket 的定位
============================================================

核心原则：

WebSocket = 实时
Database + Sync = 可靠

实时链路：
Client
→ Gateway
→ Message Service
→ DB Commit
→ ACK Sender
→ Deliver Receiver

恢复链路：
Client reconnect
→ Sync after cursor/seq
→ Server 返回缺失事件
→ Client 幂等写入本地数据库

因此即使：
- WS 丢事件
- 手机切网
- App 被杀
- iOS/Android 后台冻结
- Gateway 重启

仍可通过 Sync 恢复。

============================================================
7. 消息 ID 至少三层
============================================================

clientMsgId
- 客户端发送前生成
- UUID/ULID
- 自动重试不变
- 防止重复写入

serverMsgId
- 服务端全局唯一
- 消息永久身份

conversationSeq
- 服务端按会话分配
- 单调递增
- 排序、同步、已读、gap detection

示例：

{
  "clientMsgId": "...",
  "serverMsgId": "...",
  "conversationId": "...",
  "conversationSeq": 1088,
  "senderId": "...",
  "type": "text",
  "payload": {...},
  "serverTime": ...
}

============================================================
8. ACK 必须有清晰语义
============================================================

不要只有 success=true。

建议状态：

LOCAL_CREATED
SERVER_ACCEPTED
SERVER_PERSISTED
DELIVERED
READ
FAILED

客户端“可靠发送成功”的最低点建议：
SERVER_PERSISTED

不能以：
WebSocket socket.write 成功
作为消息成功。

============================================================
9. 重试规则
============================================================

自动重试仅针对：
- timeout
- temporary unavailable
- network disconnected

不可自动重试：
- blocked
- permission denied
- banned
- invalid payload
- stranger message limit
- message too large

所有重试复用 clientMsgId。

============================================================
10. 会话同步
============================================================

禁止启动时：
“全量拉所有会话 + 所有消息”。

一级同步：
Conversation Delta

客户端保存：
conversationCursor

GET /sync/conversations?cursor=x

返回：
- changed conversations
- tombstones
- nextCursor

二级同步：
Message Delta

客户端保存：
lastSyncedSeq

GET /conversations/{id}/sync?afterSeq=x

返回：
- messages/events
- latestSeq
- hasMore

新设备：
Bootstrap 分页获取初始快照。

老设备：
只做 Delta。

============================================================
11. 未读数
============================================================

客户端 +1/-1 只能作为 UI 乐观更新，
不能作为真相源。

服务端必须维护权威未读状态。

建议：
latestSeq
readSeq
unreadCount

如果有“不计未读”消息：
消息必须带 countAsUnread。

reconnect 后：
客户端必须以服务端状态纠偏。

============================================================
12. 撤回/编辑/删除应该事件化
============================================================

建议事件：

MESSAGE_SENT
MESSAGE_RECALLED
MESSAGE_EDITED
REACTION_ADDED
REACTION_REMOVED

离线设备上线时可补到：
“消息在离线期间被撤回/编辑”。

============================================================
13. 本地数据库
============================================================

建议表：

messages
conversations
sync_state
pending_outbox
users_cache

必须支持：
- index
- pagination
- schema migration
- cache trim
- corruption recovery
- DB size metrics
- vacuum/compact 策略

媒体文件不要以 blob 无限写入 SQLite。

只保存：
- mediaKey
- URL
- localPath
- thumbnailPath
- metadata

============================================================
14. Outbox 模式
============================================================

发送前先写本地 outbox：

clientMsgId
conversationId
payload
retryCount
nextRetryAt
status

优点：
- App 崩溃后可恢复 pending send
- 网络恢复后继续发
- 发送状态不依赖内存 Future

SERVER_PERSISTED 后：
删除或完成 outbox。

============================================================
15. Seq Gap 恢复
============================================================

例如：
lastSeq=100
实时收到 seq=105

说明存在 gap 101~104。

流程：
进入 SYNC_REQUIRED
→ sync(afterSeq=100)
→ 幂等合并

必须限制：
- 单次拉取数量
- 分页
- 重试次数
- gap 任务去重
- 本地 DB 容量

============================================================
16. 连接状态机
============================================================

不要堆一堆 bool。

推荐：

IDLE
CONNECTING
AUTHENTICATING
SYNCING
READY
RECONNECTING
KICKED
TOKEN_EXPIRED
CLOSED

连接实体至少包含：

userId
deviceId
sessionId
connectionId
tokenId

============================================================
17. 心跳和重连
============================================================

必须支持：
- 网络切换
- exponential backoff
- jitter
- 最大退避时间
- 前台快速恢复
- 后台遵守系统限制

禁止所有客户端同一秒重连，
避免 reconnect storm。

============================================================
18. Presence
============================================================

推荐：

ONLINE
RECENTLY_ACTIVE
OFFLINE
UNKNOWN

服务器 TTL 驱动。

Presence 属于 best effort，
不要依赖它做关键业务一致性。

============================================================
19. Push
============================================================

Push payload 建议只包含：

type
conversationId
serverMsgId
preview
badgeVersion
deepLink

不要无条件携带完整敏感私聊正文。

必须支持：
- 用户免打扰
- 会话免打扰
- 前台不弹系统 Push
- Push token 失效清理
- 撤回后最终以消息 Sync 状态为准

============================================================
20. 社交 App 消息权限
============================================================

业务规则必须在服务端最终校验。

例如：

FIRST_MESSAGE_AVAILABLE
WAITING_FOR_REPLY
NORMAL

未匹配：
允许第一条。

发送后：
WAITING_FOR_REPLY。

对方回复：
NORMAL。

匹配成功：
NORMAL。

Flutter 只负责 UI 状态；
服务端 MessagePermissionService 才是最终裁决者。

============================================================
21. 内容审核
============================================================

不要把所有审核都同步阻塞消息主链路。

建议：

文本：
快速规则 + 外部审核适配器

图片/视频：
对象存储上传
→ 审核
→ 正式投递或先发后审（由产品决定）

审核系统必须支持：
- 后置屏蔽
- 风控删除
- 举报取证

============================================================
22. Webhook
============================================================

建议字段：

eventId
eventType
occurredAt
schemaVersion
payload
signature

消费端按 eventId 幂等。

Webhook 与核心消息事务解耦。

============================================================
23. Transactional Outbox
============================================================

强烈建议服务端使用：

BEGIN
INSERT message
INSERT outbox_event
COMMIT

Worker：
读取 outbox
→ online delivery
→ push
→ webhook

外围服务失败，
不能导致已经成功写库的消息消失。

============================================================
24. 数据库
============================================================

V1 优先使用关系数据库完全可行。

不要因为“IM”三个字就盲目：
Mongo
Kafka
分库分表

先做好：
- unique constraints
- index
- transaction
- backup
- restore
- slow query
- load test

复杂化必须由真实数据驱动。

============================================================
25. 多端同步规则必须产品先定义
============================================================

提前确认：

同一用户是否能：
- iPhone + Android 同时在线
- 手机 + Web 同时在线

是否同步：
- 自己发送的消息
- read 状态
- 会话删除
- 撤回
- 草稿
- mute

没有明确规则前不要开始写多端逻辑。

============================================================
26. 消息 Schema 版本
============================================================

每条自定义消息：

{
  "type": "gift",
  "version": 1,
  "payload": {...}
}

要求：
- 新客户端能读旧消息
- 旧客户端遇到新消息不崩
- 未知字段忽略
- 未知消息类型显示“当前版本暂不支持”

============================================================
27. 自定义消息 Registry
============================================================

建议注册：

text

每种消息定义：

validator

29. 防滥用
============================================================

社交 IM 必须预留：

30. 可观测性
============================================================

必须监控：

SERVER_PERSISTED latency

31. Trace
============================================================

每次逻辑发送至少关联：

permission
DB commit

============================================================
32. 日志隐私
============================================================

生产日志默认不要输出：

完整聊天正文
token
手机号
精确位置
长期有效签名 URL

优先记录：

messageId
type
size
errorCode
latency
userId/hash

============================================================
33. 媒体消息
============================================================

正确流程：

Client
→ 获取 upload credential
→ 直接上传对象存储
→ 得到 mediaKey
→ 发送 IM metadata

不要把图片/语音/视频二进制通过 WebSocket 发。

消息只携带：

mediaKey
width
height
size
duration
mime
thumbnail

============================================================
34. 媒体 URL
============================================================

数据库优先存：
mediaKey

如果私有资源：
客户端临时获取 signed URL。

不要永久保存即将过期的 signed URL 作为历史消息唯一地址。

============================================================
35. 时间
============================================================

serverTime 是权威时间。

客户端时间：
只能用于本地临时展示。

不要根据客户端 createdAt 决定最终排序。

============================================================
36. 删除语义
============================================================

必须区分：

deleteForMe
recall
adminRemove
conversationClear

否则多端同步和历史恢复会混乱。

============================================================
37. 黑名单行为
============================================================

腾讯云官方允许配置：
被拉黑后发送方“显示成功但对方不收”，
或直接返回失败。

说明这属于产品策略。

NewIM 必须由产品明确选择，
不能由工程师自行决定。

============================================================

返回：

客户端进入：
REBUILD

重新 Bootstrap。

不要无限重试过期 cursor。

→ 用户进入聊天再继续历史分页

不要登录瞬间拉所有历史。

54. 服务端发送流程
============================================================

1. authenticate session
2. validate payload
3. rate limit
4. permission check
5. moderation gate
6. BEGIN TX
7. allocate conversationSeq
8. INSERT message
9. UPDATE conversation latest state
10. INSERT transactional outbox
11. COMMIT
12. ACK sender SERVER_PERSISTED
13. async online delivery
14. async offline push
15. async webhook

13/14/15 失败：
不能回滚已经持久化的核心消息。

============================================================
55. 客户端收消息流程
============================================================

收到实时事件：

1. validate schema
2. check serverMsgId
3. check conversationSeq
4. gap -> trigger sync
5. local DB transaction
6. idempotent insert
7. update conversation
8. update unread
9. commit
10. notify UI

不要先通知 UI 再写 DB。

============================================================
56. 登录流程
============================================================

init local DB
load session
connect
authenticate
protocol negotiation
conversation delta sync
critical gap sync
READY

READY 前：
可以展示缓存，
但 UI 要知道“正在同步”。

61. 几种 IM 中应该弃掉的做法
============================================================

弃 1：
WebSocket write success = 消息成功。

弃 2：
只靠 timestamp 排序。

弃 3：
重试时生成新 messageId。

弃 4：
每次启动全量同步全部会话。

弃 5：
在 UI 层做最终去重。

弃 6：
未读数只靠本地 +1/-1。

弃 7：
Push 当消息真相源。

弃 8：
typing/presence 永久入库。

弃 9：
多实例仍使用单机连接模型。

弃 10：
权限仅客户端校验。

弃 11：
Webhook 同步阻塞主消息事务。

弃 12：
没压测就先 Kafka/分库分表。

弃 13：
每个页面维护自己的底层 listener。

弃 14：
没有协议版本。

弃 15：
无限增长本地数据库。

63. NewIM 十条不可违反原则
============================================================

1. clientMsgId 重试不变。
2. 持久化后才返回可靠发送成功。
3. WebSocket 不是数据库。
4. Push 不是消息真相源。
5. sequence 不依赖客户端时间。
6. 所有业务权限服务端再次校验。
7. sync 必须幂等、分页、可恢复。
8. 本地 DB 必须可迁移、可裁剪、可重建。
9. 异步副作用使用可靠 outbox。
10. 没有可观测性就不能宣称“稳定”。

============================================================
64. 商用上线 Gate
============================================================

以下任一未完成，不建议称为“NewIM 商用稳定版”：

[ ] ACK 丢失重试不会重复
[ ] 断网重连自动补齐
[ ] App Kill 后恢复 pending send
[ ] seq gap 可恢复
[ ] unread 重连后纠正
[ ] Push 与真实消息一致
[ ] blacklist / stranger limit 服务端生效
[ ] DB migration 有测试
[ ] token expire / kicked 有状态机
[ ] Gateway restart 不丢历史消息
[ ] Push 宕机不影响消息入库
[ ] Webhook 宕机不影响消息入库
[ ] serverMsgId 可追踪完整链路
[ ] 有 P95/P99 基准
[ ] 有恢复演练
[ ] 有协议兼容测试
[ ] 有 Flutter 真机弱网测试
[ ] 有 iOS/Android 后台恢复测试

67. 最终结论
============================================================

NewIM 不应该“复制 OpenIM”。

正确方向是：

从 OpenIM 公开 Issues/PR 提前避开：
- 重连状态竞争
- Seq Gap
- 本地 DB 膨胀
- 超大会话同步
- presence 状态问题

从融云公开文档吸收：
- ACK 不确定
- 重试重复
- 去重与未读一致性

从腾讯云 IM 公开文档吸收：
- SEQ
- 分页历史
- 多端策略
- Push 分层
- Webhook
- 消息持久化分类

然后独立形成 NewIM 自己的：
- 协议
- Flutter SDK
- Server
- Sync
- DB schema
- 监控运维
- 灰度升级
- 故障恢复

真正的商用标准不是“功能看起来像成熟 IM”，而是：

在弱网、重连、重复、乱序、离线、升级、Push 故障、Webhook 故障、Gateway 重启时，
系统仍能恢复到一个确定、可解释、可追踪的一致状态。
